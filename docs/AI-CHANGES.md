# Changing tools: the recipe for AI agents

This is the one ordered path for adding or changing a tool. It is the same path as the worked example in [CONTRIBUTING.md](../CONTRIBUTING.md#worked-example-add-a-read-tool). Constraints and setup are in [AGENTS.md](../AGENTS.md); the file index is [llms.txt](../llms.txt).

## Recipe

1. **Implement.** Add the tool inside `register(mcp, deps_fn)` of the right module under `src/unifi_fabric/families/`, decorated with `@mcp.tool(...)`. Return the upstream body unchanged (the pass-through rule in AGENTS.md). Document every argument in the docstring `Args:` section; the schema descriptions are lifted from it.
2. **Register.** A new module, or a new `register_<n>` function, is registered by adding its step to the explicit loader map (`src/unifi_fabric/catalog/loaders.py`) at its place in the tools/list order; `server.py` is not edited, and `python scripts/gen_loaders.py --check` fails until the step is there. A tool in an existing module is registered by its decorator. Put the tool in a family: add its line, with its family and step, to the explicit inventory (`src/unifi_fabric/catalog/membership.py`; `python scripts/gen_membership.py --check` names a missing, duplicate or unknown tool, and the server refuses to start until it is there), and add a README domain row (`DOMAINS` in `scripts/gen_catalog_figures.py`); an unclassified tool fails the generators.
3. **Schema and annotation derivation.** Do not hand-judge annotations or schemas. Pass the shared `READ_ONLY` or `WRITE` constant from `src/unifi_fabric/tool_annotations.py` in the decorator, as sibling tools do; the final four MCP hints are derived from the code at startup. The input schema comes from the signature and docstring. Refresh the committed baseline with `python3 scripts/gen_tool_input_schemas.py --write`.
4. **Focused and invariant tests.** Add `tests/test_<module>.py` cases: a happy path, an error path, and a multi-key routing case for any tool that resolves hosts or keys (use the shared `multikey_client` fixtures). Run the module's tests and the invariant files: `pytest tests/test_<module>.py tests/test_cross_tool_invariants.py tests/test_tool_schema_contract.py tests/test_api_sources.py -n 4`.
5. **Changelog fragment.** Add one `changelog.d/<name>.added.md` file (see `changelog.d/README.md`). Do not edit `CHANGELOG.md`.
6. **Regenerate.** Run the generators in the table below, then each one's `--check`.

## The three invariants

A minimal wrapper that returns upstream JSON is not enough. Every tool must also hold these:

1. **Spec-derived optional arguments, omitted keys absent.** Optional arguments are derived from the pinned upstream specification, not guessed. When the caller leaves an optional argument unset, the key is absent from the request (query string or body); the tool never sends `null`, an empty string or an invented default in its place.
2. **Paging through the shared helpers.** A list tool pages with the shared list-drain and continuation helpers in `src/unifi_fabric/shared_shapes/_pagination.py` (`_pagination.collect_cursor`, `_pagination.collect_offset`, `_pagination.collect_links`, `_pagination.collect_batch`) and `src/unifi_fabric/shared_shapes/_continuation.py`, never a private loop. By default it drains every page, including a full final page, and marks a capped drain `incomplete`. See [PAGINATION.md](PAGINATION.md). The tests are `tests/test_pagination_contract.py` and `tests/test_pagination_drains.py`.
3. **An `api_source_id` row.** Every tool needs its classification row in `src/unifi_fabric/generated_api_facts/_api_source_table.py` (the `TOOL_API_SOURCES` entry naming the app and source pairs it calls). An unclassified tool fails catalog validation. The file is generated: run `python -m tests.api_sources_gen --write`, then `ruff format` it; `tests/test_api_sources.py` fails when the committed table differs.

The behaviour baseline in `tests/fixtures/behavior_baseline/` freezes what a caller sees: tool names, order, schemas, annotations, descriptions, results, errors and policy refusals. A change that must not alter behaviour (a move between modules, a refactor) leaves every file byte-equal, and `python3 scripts/dump_tool_baseline.py --compare l1 --base-ref origin/dev` proves it. A change to one family's tools regenerates that family's file (`python3 scripts/dump_tool_baseline.py`, then `--compare l3 --family <family> --base-ref origin/dev`); a description pass changes only descriptions (`--compare l2`). `tests/test_behavior_baseline.py` runs the check in the `test` job. It is not in the generator table because its check flag is `--verify`, not a `--check` of the docs job.

`python3 scripts/check_markdown.py` is not a generator but runs in the same `docs` job: table shape and relative links across every Markdown file.

`python3 scripts/check_retired_settings.py --check` (no retired setting name outside the changelog) and `python3 scripts/docs_claim_ledger.py --check` (every documented setting, tool name and count is real) also run in the `docs` job, through `scripts/regen_docs.py --check`. A script that gains a `--check` mode must be added to `GENERATORS` there or get a step of its own in that job; an inventory test fails otherwise.

One more script takes `--check` in a workflow but writes no tracked file. `scripts/refresh_dependencies.py --check` (the `dependency-refresh` workflow) verifies the seven managed pin files against `dependencies/manifest.toml`, and without a flag it re-resolves them.

## Family source layout

Each family's code lives under `src/unifi_fabric/families/<family>/`. A family that has moved to the layout of [public #42](https://github.com/swkstudios/unifi-fabric-mcp-server/issues/42) keeps its handlers in `handlers.py`, its routes and argument shapes in `schemas.py`, its tool wrappers in `registrar.py` and its tests in `tests/test_<family>_family*.py`; the vpn family's DNS tools are the first. Every registration step is an entry of the explicit loader map, `src/unifi_fabric/catalog/loaders.py`, in tools/list order; an entry keeps its `origin` when its family moves, so no tool's search vocabulary changes. Code that two or more families use goes in the common package, `src/unifi_fabric/shared_shapes/`, never in another family's directory; a helper only one family uses stays in that family as a private `_*.py` module. A registrar calls its handlers through the module (`handlers.<name>`). `python scripts/gen_loaders.py --check` compares the map with the directories. Which family each tool belongs to is authored in the explicit inventory, `src/unifi_fabric/catalog/membership.py`, not derived from source; a family move changes only its tools' steps there (`python scripts/gen_membership.py --generate`).

## Ownership

- **Lock files.** `requirements.lock`, `requirements-runtime.lock` and `requirements-build.lock` are produced from `pyproject.toml` and `requirements-build.in` with hashes. Do not edit them by hand and do not change dependencies in a tool PR; dependency updates are their own change, reviewed by the maintainers.
- **Changelog fragments.** Contributors add a fragment in `changelog.d/`; maintainers fold fragments into the in-flight release section at release time. A released section is never rewritten, and no generator may change one.
- **Maintainer-only release metadata.** The version in `pyproject.toml`, `server.json`, `gemini-extension.json`, the plugin manifests, `packaging/homebrew/unifi-fabric-mcp-server.rb`, `docs/site-stats.json` and the version line of [llms.txt](../llms.txt) move together at release. Contributors leave them alone; `python3 scripts/check_server_json_version.py` guards the pair `pyproject.toml` and `server.json`. `python3 scripts/pypi_readme.py --check README.md` runs in `.github/workflows/publish-pypi.yml` at publish time and is maintainer-only.
